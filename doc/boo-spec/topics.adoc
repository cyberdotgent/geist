[[topics]]
== Topics and Documentation Pages

BookManager documentation pages are stored as logical topics. A topic is a
range of decoded logical records, not a physical 4096-byte page and not a raw
SGML file. The table of contents points at topics by their public topic
identifier, while random access uses a directory topic-start index.

[[topics_topic_addressing_model]]
=== Topic Addressing Model

A topic is addressed by number, not by scanning for a marker:

. Topic number `n` (1-based) yields a start logical-record number from the
topic-start index at directory offset `0x003c`.
. The topic occupies logical records `[start(n), start(n + 1))`. For the last
topic, the terminal bound is `total_logical_records + 1`, the value at
directory offset `0x0036` plus one.
. There is no topic-end marker in the record stream. Topic size is
`start(n + 1) - start(n)`.

This is verified purely from fixtures. In the books tabulated under <<topics_directory_fields,Directory Fields>>, every value in the topic-start index
resolves to a decoded logical record that begins with an `SH<id>` topic header,
and the entry count matches directory field `0x003e`. The `SH12-565.boo`
counter-example below shows why the index, and not a scan for leading `SH`, is
authoritative.

[[topics_directory_fields]]
=== Directory Fields

The directory fields used for topic storage are:

[cols=">15,<45",options="header"]
|===
|Directory field |Meaning

|`0x0034` |Offset in the directory page of the content-page logical-record index.
|`0x0036` |Total logical-record count.
|`0x0038` |Content logical-page count.
|`0x003a` |First content logical page, relative to the directory page.
|`0x003c` |Offset in the directory page of the topic-start index.
|`0x003e` |Topic count. This matches decoded `CTOPICS`.
|===

The topic-start index at directory offset `0x003c` uses the same 16-bit paged
index format documented in <<toc>>. Each
table has the shape:

[source,c]
----
struct BooU16IndexTable {
  uint16_t count_be;             // Values stored in this table; the root holds at most 248 (0x00f8).
  uint16_t next_page_be;         // 0 in the last table; otherwise the 1-based logical
                                 // page (relative to the directory page, like 0x003a)
                                 // holding the next table at page offset 0.
  uint16_t value_be[count];      // 1-based ordinal lookup uses value[ordinal - 1].
};
----

When the topic count at `0x003e` is at most 248 the root table is direct
(`next_page_be` is `0`). Larger books split the index into a chain: the root
holds the first 248 starts and `next_page_be` names the continuation page,
whose table starts at offset `0` of that page and repeats the same layout.
Continuation values keep ascending from the root's last value, a continuation
table may hold far more than 248 values (`IBMMMSTR.boo` stores the remaining
1429 in one table), and the chain is complete when exactly `topic count`
values have been read. Verified by
parsing every bundled book and matching every decoded `SH<id>` header record:

[cols="<14,>17,<45,<45,<45",options="header"]

l|DREICMST.boo |`0x0176` (374) |directory page `0x006`: `00f8 003e ...`, last value 495 |page `0x006 + 0x3e - 1 = 0x43`, file offset `0x43000`: `007e 0000 01f0 ...` (496 ...), last value 735 |248 + 126 starts; 753 logical records.

Every row of the table above was re-read from the fixture bytes during the
2026-08-30 documentation audit and every value in it still holds. The audit
additionally checked that the chain walk terminates with exactly `topic count`
values in all 34 fixtures, and that the sum of the 34 directory `0x003e` words
is 10,502.

The index is the authoritative topic-boundary evidence. In `SH12-565.boo`
logical record 906 (inside `BIBLIOGRAPHY.2`, records 902-906) begins with the
order number `SH19-6639` of a bibliography entry; it is not in the index and
BookServer renders it as the last line of `BIBLIOGRAPHY.2`. A reader that
detects topic headers by scanning decoded records for a leading `SH` word
would split a spurious topic there.

Two independent checks confirm the split is spurious: the record carries none
of the nine envelope controls documented above, and `SH12-565.boo`'s directory
`0x003e` is 296 while a scan-based enumeration of that book yields 297 topics.

[[topics_topic_header_record]]
=== Topic Header Record

The first decoded logical record in each topic range is the topic header. It
starts with `SH<topic_id>` and contains controls that describe the topic and
its relationship to neighboring topics.

[cols="<16,<45",options="header"]
|===
|Control |Meaning

|`SH<id>` |Public topic identifier. This is the identifier used by TOC entries and BookServer topic URLs.
|`CTOPICN` |1-based topic number. This should match the ordinal used in the topic-start index. Always carries an operand. Spelled `CTOPIC#` in version 1.0 and 1.1 containers; see <<container_containers_older_than_version_1_2>>.
|`CPARENT` |Parent topic identifier. The control is always written; the operand is absent for a top-level topic (624 of 10,502 topics).
|`CFORWARDLEVEL` |Next topic identifier at the same navigation level. Always written; operand absent in 1,931 topics.
|`CBACKLEVEL` |Previous topic identifier at the same navigation level. Always written; operand absent in 1,931 topics.
|`CSUMMARY a b c` |Display-row and child counts; see below.
|`CHDLEVEL` |Topic kind or heading level; see the complete observed value list below.
|`CSOURCEFN` |Original source member/file name. Always carries an operand.
|`ST` |Display title. Its first display line is the title; see <<logical-controls_a_topic_title_is_its_st_display_line>>.
|===

[[topics_the_envelope_is_a_fixed_nine_line_sequence]]
==== The Envelope Is A Fixed Nine-Line Sequence

The 34 `BOO/` fixtures declare 10,502 topics in total (the sum of their
directory `0x003e` words). Every one of them resolves an `ST` display line, and
in 10,501 of them the controls before it are exactly

----
SH<id>
CTOPICN <n>
CPARENT [<id>]
CFORWARDLEVEL [<id>]
CBACKLEVEL [<id>]
CSUMMARY <a> <b> <c>
CHDLEVEL :<kind>
CSOURCEFN <name>
ST [<title>]
----

one control per display line, in that order, with no control omitted and none
repeated. The order never varies and the set never varies, so a reader can
consume the envelope positionally. Zero, one or more bare `SR<id>` anchor lines
may be interleaved; only three anchor opcodes occur in that position across the
corpus — `SRHDR<id>` (3,094 lines), `SRMSG <id>` (1,664) and `SRLEN [<name>]`
(273, in `SC24-546.boo`, `SC33-033.boo` and `SC34-425.boo` only).

The single exception among the fixtures is `SC09-138.boo` topic `FRONT`:
`SH`, `CTOPICN`, `CPARENT`, `CFORWARDLEVEL`, `CBACKLEVEL`, `CSUMMARY`, then
eleven `C.REV <label>` lines, then an empty `ST`. It carries no `CHDLEVEL` and
no `CSOURCEFN`. Outside the fixtures the shape is common, so the fixed order
is an encoder habit, not a rule a reader may depend on; see
<<topics_reading_the_envelope>>.

[[topics_reading_the_envelope]]
==== Reading The Envelope

The reference reader does not validate the envelope. It renders a topic in one
pass over its display lines and treats the metadata controls as follows:

[cols="<22,<45",options="header"]
|===
|Control |Effect on the served topic

|`SH<id>` |Sets the topic id used for an empty title (below).
|`CTOPICN`, `CPARENT`, `CFORWARDLEVEL`, `CBACKLEVEL`, `CSUMMARY`, `CSOURCEFN` |None. Ignored wherever they occur; their absence changes nothing.
|`CHDLEVEL :<kind>` |Names the heading level of the title. When the topic has none, the title is served at the top level (`h1`).
|`C.<word>` lines (`C.REV`, `C.SP`, ...) |None; nothing of the line is displayed.
|`SI <entry>` lines |None in the body; the line is an index entry.
|`ST [<title>]` |The topic heading. With no payload the heading is the `SH` topic id alone.
|===

So every metadata control after `SH` is optional and their order carries no
meaning. A reader can therefore take the envelope as: the `SH` line, then any
of the seven metadata controls (each at most once in every observed version
1.2 topic; a version 1.0/1.1 summary can span several `CSUMMARY` lines, see
<<topics_topic_lines_in_older_containers>>),
interleaved with bare `SR<id>` anchors, `SRMSG` and `C.REV` lines, up to the
`ST` line. Visible text before the `ST` line does not occur.

Evidence, `SC09-138.boo` (`EDCGUIDE.BOO`) topic `FRONT`, logical record 2:

[cols="<14,<22,<45",options="header"]
|===
|Token |Bytes |Meaning

|1 |`0x6616e`-`0x6616f` |`SHFRONT`
|13-16 |`0x6617c`-`0x6617f` |`CSUMMARY 0 0 0`
|17-60 |`0x66180`-`0x661c9` |eleven `C.REV` lines (`REL2 \|` ... `DUNNO ?`)
|61-62 |`0x661ca`-`0x661cb` |line length byte, then `ST` with nothing after it on its line
|63-82 |`0x661cc`- |`C.SP 1`, `SI run-time, options`, `SI TSO, system services`
|===

Hosted BookServer (DT `19910321130500`) serves this topic as `<h1> FRONT </h1>`
followed by an empty preformatted body: no `CHDLEVEL`, so level 1; empty `ST`,
so the id; the `C.` and `SI` lines draw nothing. The same rule gives
`<H3> 8.1.1.1 </H3>` for that book's topic `8.1.1.1`, which has `CHDLEVEL :H3`
and an empty `ST`.

`CSUMMARY 0 0 0` here agrees with the field meanings below: every display line
of the body is a control line (`a` = `c` = 0) and no topic names `FRONT` as its
parent (`b` = 0). The reader never consults `CSUMMARY`.

A random sample of 1,500 books from a larger collection gives the same picture:

* 84 books carry a `FRONT` topic shaped like the one above (`SH`, `CTOPICN`,
  `CPARENT`, `CFORWARDLEVEL`, `CBACKLEVEL`, `CSUMMARY`, optional `C.REV` lines,
  empty `ST`, no `CHDLEVEL`, no `CSOURCEFN`). Some have an empty body; others
  carry a whole Licensed Program Specifications text after the `ST` line.
  Hosted BookServer heads every one checked (40 books) `<h1> FRONT </h1>`.
* `SC34-3164-00.boo` writes no `CSOURCEFN` in any of its 75 topics; the rest of
  each envelope is in the usual order. Hosted serves these topics with their
  `CHDLEVEL` levels as usual (`<H1> 4.1   Book Reader</H1>`, DT
  `20000509175449`).
* No sampled topic wrote a metadata control twice or out of the order above;
  a reader that declines such a topic loses nothing observed.

Any _other_ record that looks like a topic header is a false split. The
canonical counter-example is `SH12-565.boo` record 906, described under
"Directory Fields" below: it begins with the order number `SH19-6639`, has no
envelope at all, and is not in the topic-start index.

`C.REV` is the SCRIPT revision-code control. It occurs on 22 display lines in
four books (`IBMMMSTR.boo` `PREFACE.6` record 19 is `c.rev PREF |`, declaring
the revision character used for that book's change bars) and is the only
envelope-position control outside the nine above.

[[topics_csummary_a_b_c]]
==== `CSUMMARY <a> <b> <c>`

Verified over all 10,502 declared topics:

[cols="<8,<45,<45",options="header"]
|===
|Field |Meaning |Evidence

|`a` |The topic's display-row count: the number of the topic's body display lines that are not control lines. |Reproduced for 10,432 of 10,502 topics with a simple "line does not open with a control opcode" classifier; the 70 residual topics are attributable to the classifier, not to the field. Strong hypothesis.
|`b` |The number of topics whose `CPARENT` names this topic, i.e. its direct children. |Exact in 10,502 of 10,502 topics. Verified.
|`c` |Equal to `a` in every topic. |Exact in 10,502 of 10,502 topics. Verified.
|===

The earlier note that "in `CONTENTS`, the first and third values match the topic
count" was a two-fixture sampling artifact and is retired. In `CONTENTS`,
`a` and `c` equal the number of `CTOCE` entries in that topic — exact in all 34
books — which is the same as the directory topic count only when every topic is
listed in the TOC. That holds in 21 of 34 books; in the other 13 the two
numbers differ, sometimes by a lot (`IBMMMSTR.boo` has 1,677 topics and
`CSUMMARY 60 0 60`, `SC34-425.boo` has 822 topics and `CSUMMARY 260 0 260`).

[[topics_topic_lines_in_older_containers]]
==== Topic Lines In Older Containers

The five version 1.0 and 1.1 books (see
<<container_containers_older_than_version_1_2>>) write their topic envelopes
and bodies with the same display-line framing as version 1.2, but several
control lines carry different operands. The reference reader draws none of
them; what follows is what an implementer must skip.

*`CSUMMARY <id> <script>`.* The summary line repeats the topic id and then
carries the SCRIPT formatting controls of the source topic, joined by `#`,
instead of the three counts of version 1.2. `EDCGV1R2.BOO` topic `3.4.6`,
logical record 68:

[cols="<16,<30,<45",options="header"]
|===
|File offset |Bytes |Meaning

|`0xc916` |`0a` |Display-line length byte: 10 payload bytes follow.
|`0xc917` |`7a b8 d3 1f b8 3c b8 6e 90 9a` |`CSUMMARY`, `3.4.6`, `.SP`, `1#.SK`, `1#T7#.SK`, `1#T1#.SK`, `2`
|`0xc921` |`02` |The next line's length byte, opening `CHDLEVEL :H3`.
|===

The whole line is `CSUMMARY 3.4.6 .SP 1#.SK 1#T7#.SK 1#T1#.SK 2`, and its
operands end where its display line ends. A long summary continues on further
lines that each open with `CSUMMARY <id>` again: `EDCGV1R2.BOO` topic
`CONTENTS`, record 9, writes `CSUMMARY CONTENTS #1L17#1L16...` at `0x8805`
(length byte `0x0e` at `0x8804`) and `CSUMMARY CONTENTS 1#3L52#3L27...` at
`0x8814`. 893 `CSUMMARY` lines stand in the 773 topics of the five books.

The reader recognises the line by its first eight characters and skips it
whatever follows, wherever it stands and however often it occurs. Hosted
BookServer serves `3.4.6` (DT `19891031000000`) as the heading
`3.4.6   Transaction Processing Facility` and the body only; none of the
summary text appears in any served topic of these books. A reader can
therefore take every display line that opens with `CSUMMARY` as envelope
metadata, as many as there are, and need not read its operands.

*`C.<word>` lines.* The body carries the SCRIPT controls of the source as
control lines of their own. Over the 773 topics: `C.SK <n>` 7,689 lines,
`C.SP <n>` 712, `C.CP [<depth>]` 569, `C.PA` 38 and `C.CC <n>` 6. The opcode
is one dictionary token and is the first token after the line's length byte;
the operand is the rest of that display line. `EDCGV1R2.BOO` topic `3.4.6`,
record 68:

[cols="<16,<22,<45",options="header"]
|===
|File offset |Bytes |Meaning

|`0xc930` |`02 6f 8f` |Length byte (2), `C.SP`, `1`: line 9, after the `ST` line.
|`0xc942` |`02 6e 8f` |Length byte (2), `C.SK`, `1`: line 11, between the `SI` index line and the first body row.
|===

The length byte `02` is the same one-byte token that version 1.2 records use
as the control separator (attach control and comma); here it is the display
line's length, and a reader that frames lines by their length bytes never
sees a comma. The flattened text of the record runs `SI Transaction
Processing Facility (TPF) , C.SK 1    You can compile ...`, so only the framing
separates the control from the index entry before it and the body row after
it.

The reader skips every display line whose control name begins with `C.`,
whatever the rest of the name and whatever the operands. Hosted BookServer
serves `3.4.6` with the body rows `You can compile application programs ...`
through `... GH20-7521.` and no `C.SK`, `C.SP` or count; `C.SK` draws no
blank line either (the rows before and after it are served as adjacent lines
of one preformatted block). A reader can treat every display line opened by
a `c.`/`C.` opcode token (the letters `c` or `C` and `.` followed by letters
only) as drawing nothing, with the operands bounded by that display line.

*`CFONT` one triple per line.* Every one of the 38,766 `CFONT` lines in the
five books carries exactly one `<column> <length> <code>` triple; a row
styled in several places is preceded by several `CFONT` lines. Codes seen:
`E` (21,342), `2` (6,758), `X` (5,086), `C` (2,133), `1` (1,411), `V`, `K`,
`3`, `L`, `R`, `Q`, `G`, `5`, `P`, `W`, `4`, `8`. In every topic each run of
`CFONT` lines is followed directly by the text row it styles. `EDCGV1R2.BOO`
topic `3.4.6`, record 68:

[cols="<16,<26,<45",options="header"]
|===
|File offset |Bytes |Meaning

|`0xc99e` |`04 72 9e a7 8d` |Length byte (4), `CFONT`, `31`, `7`, `X`.
|`0xc9a3` |`05 72 b8 f4 a7 8d` |Length byte (5), `CFONT`, `39`, `7`, `X`.
|`0xc9a9` |`13 ...` |Length byte (19) of `   information provided in the #pragma linkage statements and in the header`.
|===

Columns count from 0 at the row's first cell, as in version 1.2: column 31
is the `#` of `#pragma` and column 39 the `l` of `linkage`. Hosted
BookServer serves the row as `information provided in the <tt>#pragma</tt>
<tt>linkage</tt> statements and in the header`. Likewise `CFONT 40 3 C`,
`CFONT 44 7 C` and `CFONT 52 11 C` (lines 23-25) style `TPF`, `General` and
`Information` of `   For more information on TPF, consult TPF General
Information, GH20-7521.`, served as three `<cite>` runs.

The reader reads a `CFONT` line as blank-separated words: after the opcode,
each group of three words is a column and a length (decimal) and a style
code (the first character of the third word), for as many groups as the
line holds. The triples of consecutive `CFONT` lines accumulate, and the
whole set applies to the next text row that is drawn and is then cleared.
The one-triple form is therefore the same control as the many-triple form
of version 1.2, split across lines; a reader that collects the spans of
every `CFONT` line since the last drawn row reads both.

*`SI` lines before the title.* `EHMPMST.BOO` writes subject-index lines
between `CSOURCEFN` and `ST` in 39 topics. Topic `3.2.1`, record 67: line 8
starts at `0x33b23` with length byte `04`, then `7c 55 02 3e`: `SI`,
`processing`, attach + `,`, `element`; lines 9 to 11 are three more `SI`
lines, and line 12 is `ST  Element processing`. The reader skips an `SI` line
wherever it stands, so these are index entries like any other and the topic
has no visible text before its title: hosted BookServer (DT
`19891020000000`) heads it `<H3> 3.2.1   Element processing</H3>` and shows
none of the terms. Only an `SI` that is the first token after a line's
length byte is such an entry.

An `SI` line after the `ST` line ends the title: the title is its own
display line.  `SG24-4675-00.boo` topic `1.1.2`, logical record 35: the
`ST` line opens at `0x4ED93` (length byte `0F`, then `B6` = `ST`) and ends
with `Effective?`; line 9 is empty (its length byte `00` at `0x4EDA3`); line
10 is `02` at `0x4EDA4`, then `B4` (`SI`) and `47` (`costs`).  Hosted (DT
`19960308132239`) heads the topic `1.1.2   Is Your Storage Service Cost
Effective?` and prints no `costs`.  An `SI` line may also hold the keyword
alone: `dfht4c00.boo` topic `3.3.2`, logical record 219, line 7 is the
length byte `01` at `0x4C93A` and `9C` (`SI`) at `0x4C93B`, between the
index lines `SI DFHDBnnnn, CICS` and `SI DFHDBnnnn messages`.  It names no
term and, like every index line, draws nothing.

*Dashes in titles.* These books write a dash between title words as a
dictionary token whose expansion is two box-drawing horizontals (U+2500
U+2500). `EDCIV1R2.BOO` topic `2.1`, record 44, display line 8:

[cols="<16,<34,<45",options="header"]
|===
|File offset |Bytes |Meaning

|`0xce13` |`0e` |Length byte (14).
|`0xce14` |`7d 08 5c 9b 01 08 b8 2d 34 4b 71` |`ST`, title column blank, `Chapter`, `3`, attach + `.`, blank, `Preparing`, `for`, `the`, `Installation`
|`0xce1f` |`ac 75` |One token: U+2500 U+2500.
|`0xce21` |`75` |`MVS`.
|===

The run stands inside the title, after title words on the same display line,
so it is neither the title's revision column (the cell directly after `ST`)
nor a rule line; it is drawn title text. Hosted BookServer folds U+2500 to
`_` as it does in every drawn row and heads the topic `<H1> 2.1   Chapter 3.
Preparing for the Installation __ MVS</H1>` (DT `19891031000000`); the
catalog title string carries the same `__`. 28 topics of `EDCIV1R2.BOO` and
`EDCUSER.BOO` have this shape (`EDCUSER.BOO` `8.1.6.2`, DT `19900523000000`:
`<H3> 8.1.6.2   getenv __ Retrieve Environment Variables</H3>`).

*A topic with no `ST` line.* Six `EDCUSER.BOO` topics, `8.4.2.1` to
`8.4.2.6` (logical records 1156-1176), store no `ST` line anywhere: the envelope ends
with `CSOURCEFN` and the next display line is already the first body row.
Record 1156:

[cols="<16,<34,<45",options="header"]
|===
|File offset |Bytes |Meaning

|`0xbdc18` |`03` |Length byte (3).
|`0xbdc19` |`78 cc03` |`CSOURCEFN`, `EDCULOCL`
|`0xbdc1c` |`08` |Length byte (8).
|`0xbdc1d` |`12 d558 00 2c 00 c9 20` |three blanks, `LC`, attach + `_`, attach + `CTYPE`: the row `   LC_CTYPE`
|===

The reader emits a topic heading only when it reads an `ST` line, so such a
topic has no heading at all: hosted BookServer (DT `19900523000000`) serves
`8.4.2.1` as the body alone, opening with `LC_CTYPE`, with neither the topic
number nor the contents title (`LC_CTYPE`) as a heading. The contents entry
and the catalog still carry the topic's title; only the topic page lacks one.

[[topics_toc_references_versus_storage_addresses]]
=== TOC References Versus Storage Addresses

The TOC does not store physical page addresses. A `CTOCE` entry stores a target
topic id, and that id matches the target topic header's `SH<id>` value.

For example, `QS3X36CM.BOO` contains:

----
CTOCE 0 1 1.0 Introduction
----

The target topic starts with:

----
SH1.0 ... CTOPICN 4 ... CHDLEVEL :h1 ... ST Introduction
----

Therefore the TOC's first reference is a public topic id. The actual seek path
is:

. Resolve the TOC `topic_id` to a topic number by scanning topic headers or
using a prebuilt `SH` id map.
. Use that topic number to read the start logical-record number from directory
`0x003c`.
. Read logical records from `start(topic)` up to, but not including,
`start(topic + 1)`.

The hosted BookServer URL pattern is consistent with this. The known URL
`/BOOKS/QS3X36CM/CCONTENTS?...` addresses the `CONTENTS` topic by a
case-normalized `C` plus the `SHcontents` id. This URL evidence confirms the
public addressing role of the topic id, not the physical storage address.

How a server spells a topic id in a URL is a server presentation detail and not
part of the file format: the stored id is the authority, and ids containing
punctuation (`PREFACE.2.1`, `A.0`, `FRONT_1`) reach the hosted BookServer
unchanged apart from case. A reader implementing this format must match on the
stored `SH<id>` value, not on a URL spelling.

[[topics_independent_reader_algorithm]]
=== Independent Reader Algorithm

To enumerate and address documentation pages:

. Parse page 0 and locate the directory page.
. Parse directory fields `0x0034` through `0x003e`.
. Decode the content logical-record stream with the token pipeline documented
in <<logical-controls>> and <<encoding>>.
. Read the topic count from directory `0x003e`.
. For each topic number `n`, read `start_n` from the topic-start index at
directory `0x003c`.
. Compute `end_n` as the start value for topic `n + 1`; for the final topic,
use `total_logical_records + 1`.
. Decode records in `[start_n, end_n)`.
. Parse the first decoded record as the topic header and build an id map from
`SH<id>` to topic number.
. Resolve TOC and cross-reference targets through that id map, then seek by
topic number.

[[topics_open_questions]]
=== Open Questions

* Whether the chain can extend past one continuation. No fixture needs a third
table: the root holds at most 248 values, a continuation table starts at page
offset `0` and so can hold at most `(4096 - 4) / 2 = 2046`, and the largest
book in the corpus declares 1,677 topics — inside `248 + 2046 = 2294`. A book
with more than 2,294 topics must chain twice, and that is the fixture that
would settle it. Until one exists, a reader should implement the chain as a
loop with a visited-page set rather than as "root plus one continuation":
the stored `next_page_be` is what terminates it, and the loop costs nothing.
