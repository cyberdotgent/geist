[[gdf]]
== Legacy GDF Image Payloads

This chapter documents the legacy BookManager kind `G` payload family. The BOO
container stores these payloads as byte ranges referenced by the page-0 picture
directory; the container descriptor layout is documented in <<assets>>.

[[gdf_payload_family]]
=== Payload Family

Legacy kind `G` payloads are IBM GDF (Graphics Data Format) picture streams:
a sequence of one-byte order codes with operand data, the format IBM documents
for GDDM. The container stores the stream verbatim; the hosted BookServer
serves a GIF rendered from it on demand (see <<assets>>), so hosted
images are a rendering check, not the stored bytes.

Kind `G` descriptors in this repository:

[cols=">12,<15,<45",options="header"]
|===
|Kind byte |Example fixture |First verified descriptor and payload evidence

|`0xc7` / `G` |`FA1PLMM0.boo` |Descriptor at `0x0118`: `f1 40 40 40 40 40 40 40 c7 00 48 de 00 00 01 38`; payload at `0x0138` begins `01 12 00 04 00 00 00 00 42 64 00 01 00 00 00 00...`.
|`0xc7` / `G` |`packet.boo` |Descriptor at `0x0118`: `f1 40 40 40 40 40 40 40 c7 00 08 2e 00 03 6d ca`; nine kind `G` resources, used for the worked examples below.
|===

Ten repository books carry kind `G` descriptors, 65 in total; see <<assets>> for the full census.

[[gdf_upstream_reference]]
=== Upstream Reference

The normative names and encodings for GDF orders come from published IBM
documentation, not from any reader binary. The reference used throughout this
note is `QPRG1GDR`, `SC41-0537-00`, "AS/400 GDDM Programming Reference",
Appendix B, "GDF Order Descriptions", read through the hosted BookServer
collection under `BOOKS/QPRG1GDR/B.0`.

Where an order is observed in a repository fixture but is not described in that
appendix, this book says so explicitly and marks the interpretation as
unverified.

[[gdf_payload_framing]]
=== Payload Framing

The stored kind `G` payload is a GDF record stream, not an undelimited run of
coordinate data. Every record is self-delimiting under the framing rules below,
which is what lets a decoder skip an order it does not implement.

[[gdf_ibm_short_hexadecimal_floating_point]]
==== IBM Short Hexadecimal Floating Point

Observed 4-byte GDF coordinates and header extents use IBM short hexadecimal
floating point, stored big-endian:

[cols="<17,<39",options="header"]
|===
|Byte/bit range |Meaning

|Byte 0, bit 7 |Sign. `0` is positive, `1` is negative.
|Byte 0, bits 6..0 |Base-16 exponent with excess-64 bias.
|Bytes 1..3 |24-bit unsigned fraction.
|===

The decoded value is:

----
sign * (fraction / 0x01000000) * 16^(exponent - 64)
----

where `sign` is `+1` or `-1`. A zero 24-bit fraction is the value `0.0`,
whatever the characteristic byte holds.

This is the IBM System/360-family hexadecimal floating-point format, later
called HFP by IBM. The GDF payloads use the 32-bit/single-precision member of
that family, which IBM documentation calls the short format. It is an upstream
machine data format, not a BookManager-specific floating-point encoding and not
an IEEE 754 `binary32`/C `float`.

Differences from the common IEEE 754 single-precision float:

[cols="<35,<45,<45",options="header"]
|===
|Property |IBM short HFP used here |IEEE 754 binary32

|Total size |32 bits |32 bits
|Byte order in observed GDF payloads |Big-endian |Format does not require a file byte order; memory byte order is platform-specific.
|Sign |1 bit |1 bit
|Exponent |7-bit base-16 characteristic, bias 64 |8-bit base-2 exponent, bias 127
|Significand/fraction storage |24 explicit fraction bits with the radix point to the left of the fraction |23 stored fraction bits plus an implicit leading `1` for normal values
|Value radix |`16` |`2`
|Finite-value formula |`(-1)^sign * 0.fraction_hex * 16^(characteristic - 64)` |`(-1)^sign * 1.fraction_bin * 2^(exponent - 127)` for normal values
|Special encodings |No IEEE-style infinities, NaNs, or subnormal class in the observed coordinates; zero is a zero fraction |Exponent fields `0x00` and `0xff` encode zero/subnormal and infinity/NaN classes
|Effective precision |Six hexadecimal fraction digits. In binary terms this can wobble because base-16 normalization can leave up to three leading zero bits in the binary significand. |24 binary significant bits for normal values
|===

Implementation notes:

. Read the four bytes as one big-endian 32-bit word.
. If the 24-bit fraction field is zero, return `0.0`.
. Let `sign` be negative when bit 31 is set.
. Let `characteristic = (word >> 24) & 0x7f`.
. Let `fraction = word & 0x00ffffff`.
. Decode as:

----
(-1 if sign else +1) * (fraction / 16777216.0) *
    16^(characteristic - 64)
----

Equivalently, `16^n` can be evaluated as `2^(4*n)`.

The observed BookManager/GDF payloads do not show a deviation from standard IBM
short HFP for 4-byte coordinates. The only GDF-specific rule observed so far is
where the values are stored: the picture header and 4-byte coordinate record
fields use this format. A header length of `0x02` instead selects a 2-byte
coordinate encoding; no repository fixture uses it, so that path is unverified
here.

Examples from `FA1PLMM0.boo` resource 1:

[cols="<13,>18",options="header"]
|===
|Bytes |Decoded value

|`00 00 00 00` |`0.0`
|`42 64 00 01` |`100.000015258789`
|`42 64 00 06` |`100.000091552734`
|===

[[gdf_picture_header]]
==== Picture Header

The stream begins with a variable-length header:

[cols=">8,>8,<45",options="header"]
|===
|Offset |Size |Meaning

|`0x00` |1 |Header introducer. `0x01` in every kind `G` payload observed; in IBM's terms this is the comment order code.
|`0x01` |1 |Header payload length in bytes. `0x12` in every kind `G` payload observed.
|`0x02` |2 |Coordinate data type. `00 04` (System/370 floating point) in every kind `G` payload observed.
|`0x04` |4 |Minimum X as IBM short hexadecimal floating point.
|`0x08` |4 |Maximum X as IBM short hexadecimal floating point.
|`0x0c` |4 |Minimum Y as IBM short hexadecimal floating point.
|`0x10` |4 |Maximum Y as IBM short hexadecimal floating point.
|===

For `FA1PLMM0.boo` resource 1, bytes `00 00 00 00 42 64 00 01 00 00 00 00 42 64 00 06` at payload-relative offsets `0x04..0x13` decode to an extent of
approximately `x=0..100.000015`, `y=0..100.000092`. `SC34-425.boo` resource 1
carries the identical header; `packet.boo` resource 1 carries the same shape
with exact `100.0` bounds (`42 64 00 00`).

The header length selects the coordinate encoding: `0x02` selects a 2-byte
path, other lengths the 4-byte IBM hexadecimal-floating path reading the four
window values at offsets `0x04..0x13`. Every observed kind `G` payload (928
pictures in a 60-book sample, all of `KAKHMST.BOO` and `packet.boo`) uses
header length `0x12` and data type `00 04`; the 2-byte path is unverified.

[[gdf_ibm_gdf_order_structure]]
==== IBM GDF Order Structure

IBM documents GDF as a sequence of one-byte order codes, each followed by
operand data. The upstream reference used for the order names below is
`QPRG1GDR`, `SC41-0537-00`, "AS/400 GDDM Programming Reference", Appendix B,
"GDF Order Descriptions", read through the hosted BookServer collection as book
`QPRG1GDR`, topic `B.0`.

Important IBM reference topics:

[cols="<8,<45",options="header"]
|===
|Topic |Evidence used

|`B.1` |Initial comment order encodes the window coordinates and data type. Data type `4` means System/370 floating point.
|`B.2` |Lists GDF order names and code values.
|`B.5.1` |Normal format is order code, one-byte length, then operand bytes.
|`B.5.2` |Short format omits the length; high nibble `< 8` and low nibble `>= 8` means one operand byte.
|`B.7` |AS/400 GDDM uses 2-byte signed coordinates, while the BookManager fixtures here use the System/370 floating-point coordinate type from the initial comment.
|`B.11.1` |Character Mode order values: default, string precision, character/image precision, and stroke/vector precision.
|`B.11.2` |Character orders `0xc3`/`0x83`: optional coordinate followed by EBCDIC character bytes `>= 0x40`; current position is not changed.
|`B.11.3` |Character Set order `0x38`: one-byte local character-set identifier; `0x00` is default and `0x41..0xdf` are user-defined sets.
|`B.11.4` |Character Shear order `0x35`: vector defining upright-stroke shear relative to the baseline.
|`B.11.5` |Color order `0x0a`: one-byte value is an index into the default color table.
|`B.11.6` |Color Set Extended order `0x26`: two-byte value is an index into the color table. BookManager packet figures use this order rather than `0x0a`.
|`C.1` |Color numbers and default GDDM color definitions, including extended colors `9..16` and the repeat rule for higher values.
|===

The first BookManager bytes called the picture header above are therefore the
initial GDF comment order. For `FA1PLMM0.boo` resource 1, payload bytes
`01 12 00 04 ...` are:

[cols=">12,<18,<45",options="header"]
|===
|Offset |Bytes |IBM GDF interpretation

|`0x00` |`01` |Comment order code.
|`0x01` |`12` |Comment payload length, 18 bytes.
|`0x02` |`00 04` |Coordinate data type `4`: System/370 floating point.
|`0x04..0x13` |four 4-byte values |X low, X high, Y low, Y high, decoded as IBM short HFP.
|===

[[gdf_record_header]]
==== Record Header

Records begin at payload-relative offset `2 + header_length`. Read a one-byte
opcode, then determine the payload length as follows:

[cols="<39,<40",options="header"]
|===
|Opcode condition |Payload length rule

|Opcode `0x00` |Length is zero.
|High nibble `< 8` and low nibble `>= 8` |Length is implicitly one byte.
|All other non-zero opcodes |Next byte is an unsigned payload length.
|===

The payload immediately follows the optional length byte. Unknown records can
therefore be skipped by this length rule.

[[gdf_prologs]]
==== Prologs

Between the initial comment and the first drawing order a payload may carry up
to two prologs, each a run of records with opcode `0x02`. A prolog opens with
the three bytes `02 02 xx`, where `xx` is `01` for a font list and `02` for
picture attributes; the font list, when present, comes first. Inside a prolog:

* a record whose payload is two bytes is a marker: second payload byte `0x7e`
  opens the prolog, `0x7f` closes it;
* any other record is an entry; its second payload byte names the entry;
* a single `0x00` byte may follow any record and is padding.

A font-list entry associates a local character-set id with an eight-byte
EBCDIC GDDM symbol-set name: payload byte 4 is the id, bytes 5..12 the name,
blank padded; eight more blanks follow. Evidence, `GC24-5673-01.boo`
resource 17, payload offsets `0x14..0x33`:

----
02 02 01 7e
02 15 01 40 02 00 41 c1 c4 d4 e4 e4 e2 d9 d7 40 40 40 40 40 40 40 40 00
02 02 01 7f
----

One entry: id `0x41`, name `ADMUUSRP`. In the sampled library, font lists
name `ADMUU...` and `ADMUW...` sets under ids `0x41..0x44` and `0xc8..0xd8`,
and `DZB` and `ADMDHI...` under id `0x00`. Whatever the names, the reference
renderer sets all text of a picture with a font list in one proportional face
(<<gdf_text_and_font_handling>>).

Picture-attribute entries observed:

[cols=">10,<30,<45",options="header"]
|===
|Entry |Payload |Meaning

|`0x0e` |`02 0e 80` |No effect on the rendered picture.
|`0x32`, `0x27` |`02 xx 12 00 3c 00` + four coordinates |Window repeats; no effect on the rendered picture.
|`0x20` |`02 20 08` + two coordinates |Picture aspect: page width `w`, then height `h`.
|`0x01` |`80 01 08 00 ...` |No effect on the rendered picture.
|===

The aspect entry scales the coordinate space: with `m = max(w, h)`, x
coordinates are multiplied by `m / w` and y coordinates by `m / h` before
drawing, and the window grows by the same factors. Because the window is
scaled with the drawing, the aspect does not change where a point lands on the
canvas (see <<gdf_canvas>>); it matters for arcs, which are circular in the
scaled space, and for model-transform translations, which are not scaled.

The hosted reference renderer also accepts entries `0x0c`, `0x0d`, `0x10`,
`0x11`, `0x18`, `0x22`, `0x26`, `0x28`, `0x29`, `0x33` to `0x3a` and `0x43`
without visible effect, and rejects the picture for any other entry.

Evidence, `KAKHMST.BOO` resource 1 (payload at file offset `0x000652ce`),
payload offsets `0x14..0x6d`:

----
02 02 02 7e  02 03 02 0e 80  02 15 02 32 12 00 3c 00 00000000 42640001 00000000 42640006
02 15 02 27 12 00 3c 00 00000000 42640001 00000000 42640006
02 0b 02 20 08 4060aab0 4083f7fe 00
02 0b 80 01 08 00 00 00 00 00 00 00 00  02 02 02 7f
----

The aspect is `w = 0.3776`, `h = 0.5155`: x scales by `1.3652`, y by `1`.
All 30 kind `G` pictures of `KAKHMST.BOO` and pictures 2..6 and 9 of
`packet.boo` carry this same prolog.

[[gdf_gdf_orders]]
=== GDF Orders

The table below is the set of orders a BookManager kind `G` payload can carry
and what each does to the hosted reference rendering. Names come from IBM
`QPRG1GDR` Appendix B where it names the order. Every coordinate read by an
order passes through the current model transform (<<gdf_model_transform>>);
"point" below means a transformed coordinate pair.

Orders `0x40..0x7f` whose low six bits name an attribute order are
push-and-set orders: they save the attribute's current value
(<<gdf_attribute_stack>>), then act as the plain order.

[cols=">10,<30,<60",options="header"]
|===
|Opcode |Name |Effect

|`0x00` |No-op |None.
|`0x02` |Prolog record |None outside a prolog.
|`0x03` / `0x33` |Character box |Width and height. The height is the em of later text; the width has no effect. Not transformed. See <<gdf_text_and_font_handling>>.
|`0x04`, `0x23`, `0x3e`, `0x43` |Segment attributes, comments |None. Every observed segment begins `70 ... 04 ... 3e 00 23 04 00000001`.
|`0x07` |Segment call |Replays a segment started by `0x70`. Not observed in kind `G` payloads.
|`0x09` / `0x28` |Pattern |Interior of later areas; see <<gdf_patterns>>.
|`0x0a` / `0x4a` |Color |Values `0..8` select that color number, higher values neutral (`7`). See <<gdf_colors>>.
|`0x0c` / `0x4c` |Color mix |Affects graphics images only.
|`0x0d` / `0x4d` |Background mix |`2` paints the background pixels of patterns and hatches; `1`, `3` and `4` select mixing draw modes; others overpaint. Observed value: `5`.
|`0x10` / `0x50` |Character alignment |Text alignment. Not observed.
|`0x11` / `0x51` |Fractional line width |None: lines stay one pixel wide. Observed `0100`, `0200`, `001a`, `0280`, `0300`.
|`0x18` / `0x58` |Line type |See <<gdf_line_types>>.
|`0x19` / `0x59` |Line width |Integer line width. Not observed.
|`0x21` / `0x61` |Current position |Sets the current position to the point.
|`0x22` / `0x62` |Arc parameters |See <<gdf_arcs>>.
|`0x24` / `0x64` |Model transform |See <<gdf_model_transform>>.
|`0x26` / `0x66` |Color set extended |Two bytes; see <<gdf_colors>>.
|`0x27` / `0x67` |Clipping |Sets a clip rectangle. Not observed.
|`0x29` / `0x69` |Marker type |Marker symbol; see <<gdf_markers>>.
|`0x34` / `0x74` |Character angle |Text baseline direction `(x, y)`, untransformed; `(1, 0)` is upright. See <<gdf_text_and_font_handling>>.
|`0x35`, `0x39`, `0x3a` and their push forms |Character shear, mode, direction |None.
|`0x37` / `0x77` |Marker scale |None; a pop that restores a saved marker scale sets the marker size. See <<gdf_markers>>.
|`0x36` / `0x76` |Character spacing |Flag byte, padding byte, then a coordinate pair: with flag `0`, the x operand is extra advance per character; any other flag resets it to `0`. Not observed.
|`0x38` / `0x78` |Character set |Local character-set id of later text; selects the face (<<gdf_text_and_font_handling>>).
|`0x3f` |Pop |Restores the last saved attribute; see <<gdf_attribute_stack>>.
|`0x60` |Area end |Ends the current figure; see <<gdf_areas>>.
|`0x68` |Area |Flag byte; see <<gdf_areas>>.
|`0x70` |Segment start |Four-byte segment id; no drawing effect.
|`0x71` |Segment end |Ends a replayed segment; no drawing effect otherwise.
|`0x81` |Line at current position |Polyline from the current position through the points.
|`0xc1` |Line |Polyline through the points.
|`0xa1` |Relative line at current position |Signed one-byte `dx dy` pairs, accumulated from the current position.
|`0xe1` |Relative line |One coordinate pair, then signed one-byte `dx dy` pairs accumulated from it before transformation.
|`0x82` / `0xc2` |Marker |`c2` marks every point; `82` marks the current position, then every point. The current position moves to the last point. See <<gdf_markers>>.
|`0x83` / `0xc3` |Character |Text at the current position, or at the leading point; the bytes after it are EBCDIC text up to the end of the record or a `0x00` byte. The current position does not change.
|`0x85` / `0xc5` |Fillet |None: the hosted reference draws nothing for fillets.
|`0x86` / `0xc6` |Arc |Three-point arc; see <<gdf_arcs>>.
|`0x87` / `0xc7` |Full arc |Full ellipse at the current position or point, scaled by a one-byte-plus-fraction multiplier. Not observed.
|`0x91`, `0xd1`, `0x92`, `0x93` |Graphics image |Cell-array image begin, data and end. Not observed.
|other |— |None.
|===

After each line or arc order the current position is its last point.

Every line order inside a figure extends the figure (<<gdf_areas>>). Outside a
figure, line orders draw only while the line type is visible; arcs always
draw.

[[gdf_canvas]]
==== Canvas

Hosted BookServer serves every kind `G` picture as a `1004 x 735` GIF on a
white background. The picture window from the initial comment maps
anisotropically onto the pixel box x `2..998`, y `733..2` (y grows upwards).
A least-squares fit of axis-aligned line positions in hosted GIFs against
their coordinates gives:

[cols="<26,>14,>14,>14,>14",options="header"]
|===
|Picture |x slope |x at 0 |y slope |y at 0

|`KAKHMST.BOO` resource 1 |9.9659 |1.88 |-7.3082 |732.83
|`KAKHMST.BOO` resource 2 |9.9609 |1.92 |-7.3069 |732.76
|`packet.boo` resource 7 (no aspect entry) |9.9666 |1.87 |-7.2969 |732.33
|===

(`996 / 100 = 9.96`, `731 / 100 = 7.31`.) The mapping is the same with and
without an aspect entry. Lines are one pixel wide; a polyline does not draw
its final pixel.

[[gdf_colors]]
==== Colors

The color current at any time is a GDDM color number. `0x0a` with value `v`
selects `v` for `v <= 8` and `7` otherwise. `0x26` with operand bytes `a b`
selects:

[cols="<25,<20",options="header"]
|===
|Operand |Color number

|`ff 07` |`8`
|`ff 08` |`7`
|`xx 00` |`7`
|`xx 01` .. `xx 10` |`01` .. `16`
|`xx 11` and above |`7`
|===

The `ff 07` / `ff 08` swap is how most books select black: `66 02 ff 07`
occurs 30538 times in 782 of 928 sampled kind `G` pictures. In `KAKHMST.BOO`
resource 1 it is at payload offset `0x98`, right before the first line. The
initial color is `7`.

Rendered RGB, as hosted GIFs show them (`9..16` are the nearest entries of the
GIF's fixed palette):

[cols=">8,<16,<16",options="header"]
|===
|Number |Name |RGB

|`0` |Default |`0 0 0`
|`1` |Blue |`0 0 255`
|`2` |Red |`255 0 0`
|`3` |Pink |`255 0 255`
|`4` |Green |`0 255 0`
|`5` |Turquoise |`0 255 255`
|`6` |Yellow |`255 255 0`
|`7` |Neutral |`255 255 255`
|`8` |Background |`0 0 0`
|`9` |Dark blue |`0 0 128`
|`10` |Orange |`224 128 0`
|`11` |Purple |`128 0 128`
|`12` |Dark green |`0 128 0`
|`13` |Dark turquoise |`0 128 128`
|`14` |Mustard |`160 160 0`
|`15` |Gray |`128 128 128`
|`16` |Brown |`128 128 0`
|===

Neutral is white on the white canvas: a picture drawn only in color `7` is
blank. `GC33-0805-00.boo` resource 1 fills its box faces with `66 02 00 07`
and they are white in the hosted GIF. Lines, edges and text use the current
color; areas use the color current when the figure begins
(<<gdf_areas>>).

[[gdf_line_types]]
==== Line Types

`0x18` values `0..7` select a dash pattern; `8` and above make lines invisible
(and boundaries of figures begun afterwards invisible). Patterns run on along a
polyline, in pixels:

[cols=">8,<30",options="header"]
|===
|Value |On / off runs

|`0`, `7` |Solid
|`1`, `5` |`3 3`
|`2` |`18 6`
|`3`, `4` |`9 6 3 6`
|`6` |`9 3 3 3 3 3`
|===

`BLGR8MST.BOO` resource 6 draws one labelled line per value `0..8`; in its
hosted GIF the runs of rows 332 (value 1), 349 (2), 368 (3), 385 (4), 404 (5)
and 422 (6) are exactly these, and value 8 draws nothing. `KAKHMST.BOO`
resource 1 draws its feedback arrow with `58 05`; hosted row 141 alternates
three inked and three blank pixels.

[[gdf_areas]]
==== Areas

An area order `68 f` acts on its flag byte:

[cols="<20,<60",options="header"]
|===
|Flag |Effect

|bit `0x80` clear |Ends the current figure, as `0x60` does.
|`0x80` set, `0x40` clear |Begins a figure now, without boundary lines.
|`0x80` and `0x40` set |Requests boundary lines and begins the figure at the next `0x81`, `0xc1`, `0xe1` or `0xc6` order.
|===

A figure takes its fill color, interior and boundary color when it begins.
While a figure is requested but not begun, color orders do not change the fill
color. Inside a figure, `0xc1`, `0xe1` and `0xc6` start a new contour;
`0x81`, `0xa1` and `0x86` continue the current one. Each contour is closed.
`0x60` (or an area order without bit `0x80`) fills the figure and, if
requested, strokes each closed contour in the boundary color and line type,
then makes boundary lines visible again.

Contours fill together by the even-odd rule: a pixel is inside when a ray
from it crosses the figure's edges an odd number of times. Two consequences
show in hosted GIFs:

* an edge and its exact reverse cancel: stroke-font areas carry out-and-back
  construction edges (in `packet.boo` resource `6` area 2,
  `(70.57216,89.05028) -> (80.720,96.337)` and its reverse in the `IPv6`
  title), and the hosted GIF shows no ink along them;
* a face traced twice stays empty: `BLGR8MST.BOO` resource 10 draws its 3-D
  bars as `68 c0` figures (the first at payload offset `0x658`) whose `c1`
  runs round each face twice, `(48.1,49.1) (48.1,52.23) (50.08,54.93)
  (50.08,51.84)` and again back to the start, under dot pattern `28 04`.
  The hosted GIF shows only the boundary lines; a winding-number fill would
  cover the faces with the pattern.

Filling by the even-odd rule also leaves no stray pixels at the shared edges
of `KAKHMST.BOO` resources 2, 3, 4 and 28 and `GC33-0805-00.boo` resources 1
and 2, which a winding-number fill marks.

`packet.boo` resource 2 (file offset `0x00000238`) shows the plain form: each
filled packet-field rectangle is `26 02 00 06`, `68 80`, `26 02 00 08`, a
five-point `c1`, `60 00` (payload offsets `0x0090..0x00ca`). The figure began
at `68 80`, so it fills yellow (`6`); the later `00 08` does not change it.
Hosted pixel `(220, 310)` is `ff ff 00`.

`KAKHMST.BOO` resource 1 draws its bold headings with `68 c0` figures whose
glyph outlines are a `c1` followed by `81` continuations (record at payload
offset `0xca96` onwards); filling each `c1 81 ...` run as one contour gives
the hosted letter shapes.

[[gdf_patterns]]
==== Patterns

The pattern order selects the interior of later figures:

[cols="<16,<60",options="header"]
|===
|Value |Interior

|`0`, `16` |Solid, in the fill color.
|`1` .. `7` |Dot pattern of density `8 - value`, in black.
|`8` |Dot pattern of density 1.
|`9` |Vertical hatch: pixels with `x mod 8 = 4`.
|`10` |Horizontal hatch: pixels with `y mod 8 = 3`.
|`11`, `12` |Rising hatch: pixels with `(x + y) mod 8 = 7`.
|`13`, `14` |Falling hatch: pixels with `(x - y) mod 8 = 0`.
|`15` |Empty: no fill, boundary only.
|`0x11..0x40`, `0xff` |Solid.
|`0x41..0xfe` |Color pattern. Not observed.
|===

Dot patterns are four rows of eight pixels, most significant bit leftmost,
repeating every 8 columns and 4 rows of the canvas; canvas row `y` uses row
`3 - (y mod 4)`:

[cols=">10,<30",options="header"]
|===
|Density |Rows 0..3

|1 |`00 00 00 88`
|2 |`00 aa 44 aa`
|3 |`00 22 00 aa`
|4 |`11 aa 55 aa`
|5 |`55 aa 55 ee`
|6 |`55 bb 55 ff`
|7 |`55 ff dd ff`
|===

Hatches draw in the fill color. Both leave the other interior pixels as they
were, unless background mix `2` is in effect. Coordinates are canvas pixels.
Evidence: `packet.boo` resource 7 fills a green-edged box with `09 07`; the
hosted GIF has black pixels exactly where `x mod 4 = 0` and `y mod 4 = 0`
(rows 324, 328, ...). `BLGR8MST.BOO` resource 13 fills bars with `09 01`;
hosted rows 140..143 are full, `.###`, full, `.#.#` repeating. `DFHIS101.BOO`
resource 1 uses `09 0b` and `09 0e`; `GC24-5673-01.boo` resource 17 uses
values 2..6 and 9..14. All match the formulas above.

[[gdf_model_transform]]
==== Model Transform

The transform is a 3x3 matrix applied to row vectors:
`x' = x*m0 + y*m3 + m6`, `y' = x*m1 + y*m4 + m7`. It starts as the identity
scaled by the aspect factors (`m0` and `m3` by the x factor, `m1` and `m4` by
the y factor).

Order `0x24` payload: byte 0 reserved, byte 1 mode (low two bits), byte 2
mask 1, byte 3 mask 2, then one coordinate for each set mask bit, mask 1 bits
7 down to 0 and then mask 2 bits 7 down to 0. Elements not given keep their
identity value:

[cols="<20,<40",options="header"]
|===
|Mask bit |Element

|mask 1 bit 7, 6 |`m0`, `m1`
|mask 1 bit 4, 3, 2, 0 |`m2`, `m3`, `m4`, `m5`
|mask 2 bit 3, 2, 0 |`m6`, `m7`, `m8`
|other bits |value read and ignored
|===

Mode `0` replaces the matrix (then scales it by the aspect factors as at the
start), mode `1` multiplies current x given, mode `2` given x current, mode
`3` changes nothing. `FIJI1MST.BOO` carries
`64 .. 00 02 cc 0c 41100000 00000000 00000000 40fffffd ...`: mode 2 with
`m0 = 1`, `m1 = 0`, `m3 = 0`, `m4 = 0.99999`, then `m6` and `m7`.

[[gdf_arcs]]
==== Arcs

Arc parameters `P Q R S` (four coordinates) are transformed as the points
`(P, S)` and `(R, Q)`; call the results `(a, d)` and `(c, b)`. They map the
unit circle to the arc ellipse: `x = a*u + c*v`, `y = d*u + b*v`. Initially
`a = b = 1`, `c = d = 0`.

An arc runs from `p0` (the current position for `0x86`, the first point for
`0xc6`) through `p1` to `p2`:

. If `|a*b - c*d| < 1e-5`, draw the polyline `p0 p1 p2`.
. Map `p1 - p0` and `p2 - p0` by `(x*b - y*c, y*a - x*d)` and find the circle
  through the origin and the two mapped points. If the three are collinear
  (`|2*(q2x*q1y - q1x*q2y)| < 1e-5`), or the start and end angles on that
  circle differ by less than one degree, draw the polyline.
. Otherwise draw the elliptical arc of the ellipse through `p0` and `p2` that
  passes through `p1`, unless its centre is beyond 50000 units or its
  conjugate-diameter points lie more than twice the window size from the
  window origin, in which case draw the polyline.

`packet.boo` resources 7 and 8 draw their circles with `62` and `c6` / `86`
orders; `OFCLRNWP.BOO` resource 18 draws pie charts the same way.

[[gdf_markers]]
==== Markers

Marker type `1` is a diagonal cross and `2` an upright cross. Each is ten
pixels across, centred on the pixel its point maps to, whatever the
picture's scale and whatever the marker-scale orders say; each stroke runs
from one end to the other without its final pixel: `(-5, -5)` to `(5, 5)`
and `(-5, 5)` to `(5, -5)`, or `(0, -5)` to `(0, 5)` and `(-5, 0)` to
`(5, 0)`, in pixels. Markers take the current color. Evidence,
`BLGR8MST.BOO` resource 15: `69 01` at payload offset `0x7ee`, then
`c2 60` + 12 points at `0x800` (first point `(7.0, 84.36)`, pixel
`(72, 116)`) draws red diagonal crosses; `69 02` at `0x868` and the same 12
points at `0x870` draw blue upright crosses over them; the hosted GIF
matches pixel for pixel.

Types `0` and `3`..`10` are unobserved. Type bytes of `11` and up
(`0x45`, `0x46`, `0x4a`, `0x60`, `0x65` in `GC24-5673-01.boo` resources 8,
13, 15, 16 and 19) show in hosted GIFs as asterisk-like symbols of more than
one size; how the type byte selects them is not established. The marker
scale order (`37` / `77`, two coordinates) does not change the markers that
follow it in any observed picture.

[[gdf_attribute_stack]]
==== Attribute Stack

Push-and-set orders `0x03`, `0x09`, `0x23`, `0x4a`, `0x4c`, `0x4d`, `0x50`,
`0x51`, `0x58`, `0x59`, `0x61`, `0x62`, `0x64`, `0x66`, `0x67`, `0x69` and
`0x74`..`0x7a` save the value the order replaces. `0x3f` restores the most
recent saved value and re-applies colors. Restoring a line type does not
change whether lines are visible. A pop with nothing saved does nothing.

[[gdf_text_and_font_handling]]
==== Text and Font Handling

*Characters.* A character order's string ends at the end of the record or at
the first `0x00` byte. Every byte below `0x40` shows as a space, and so do
`0x41`, `0x8f` and `0xff`; `0x8a` shows as `G`; the other bytes follow code
page 500, which agrees with code page 037 on letters, digits and common
punctuation (`c1 c2 c3 c4` is `ABCD`). Evidence, `GC24-5673-01.boo` resource
1, payload offset `0x548`: the axis label `f9 f1 f2 f1 60 f7 f4 f2 15 d4 89 95
...` shows in the hosted GIF as `9121-742 Minidisk`, the `0x15` as a space.
The code page 500 assignments that differ from code page 037 (`0x4a`, `0x4f`,
`0x5a`, `0x5f`, `0xb0`, `0xba`, `0xbb`) and the `0x8a` exception are not
observed in the sampled pictures.

*Face.* The reference renderer has two faces: a proportional sans serif of
the Helvetica class, and a fixed-pitch face. A picture without a font-list
prolog sets text in the fixed-pitch face once a character-set order (`0x38` /
`0x78`, any id) has been applied, or a pop has restored one, and in the
proportional face before that. A picture with a font-list prolog sets all its
text in the proportional face, whatever ids its character-set orders select
and whatever its entries name. Evidence:

[cols="<34,<30,<36",options="header"]
|===
|Picture |Prolog and character set |Hosted face

|`BLGR8MST.BOO` resource 13 |no font list; `79 03 78 00` at payload offset `0x88` |fixed pitch: `DEPARTMENT XXX PLAN` advances `17.9` px per character
|`BLGR8MST.BOO` resource 10 |no font list; no character-set order |proportional: `ACTIVE PROBLEMS BY TYPE AND PHASE`
|`GC24-5673-01.boo` resource 1 |font list `0x41` `ADMUUSRP`, `0x42` `ADMUUKSF`, `0x43` `ADMUUDRP`; the title follows `78 42` |proportional, regular weight, title included
|`packet.boo` resource 1 |font list of 17 `ADMUW...` entries; text after `78 00` |proportional
|===

*Size.* The character box height, times the canvas y scale
(<<gdf_canvas>>), is the em of the face in pixels; the box width has no
effect. In `BLGR8MST.BOO` resource 13 the box `2.45 x 4.238` gives an em of
`31` px: capitals stand `20` px tall and characters advance `17.9` px. In
resource 14 the box `2.1 x 4.416` (em `32.3` px) advances `18.7` px per
character in `1990 FOCUS`, and `1.575 x 3.312` (em `24.2` px) `13.8` px in
`LOSSES`; the box widths would give `15.3` and `11.5` px. In the fixed-pitch
face capitals stand about `0.63` em and characters advance about `0.57` em;
in the proportional
face capitals stand about `0.72` em (`GC24-5673-01.boo` resource 17, box
height `3.068`, em `22.4` px, capitals `15` px).

*Position.* The text point is the start of the baseline: glyphs stand on the
pixel row just above the row the point maps to (`BLGR8MST.BOO` resource 13:
the point `(25.5, 92.69)` maps to row `55`; capitals occupy rows `35..54`).

*Angle.* The reference turns the character-angle vector into a baseline
angle with `atan2(y, x)`, adds `6.28` when the result is negative, and
converts it to whole tenths of a degree, truncating, with pi taken as
`3.141`. The text then turns about its start point; `(0, 1)` runs the string
up the page with the tops of the letters to the left. A vector a hair off an
axis therefore still gives a quarter turn: `BLGR8MST.BOO` resource 12 carries
`34 08 3d2ee13f 41100000` (`x = 0.0000447`, `y = 1`) at payload offset
`0x14e`, and its label `PERCENTAGE` is vertical in the hosted GIF.
`GC24-5673-01.boo` resource 1 carries `74 08 00000000 41100000` before the
axis title `ITR in Commands Per Processor Second`, also vertical. Other
angles are not observed.
