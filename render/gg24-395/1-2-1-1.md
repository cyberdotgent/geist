### 1\.2\.1\.1 VM Roots

Talking about the roots of VM takes us back to the early 1960's\. At that

time ideas and the philosophy of "time\-sharing" were first published\. The industry was still on the track of batch\-oriented systems for Electronic Data Processing \(EDP\)\. But researchers at universities such as the Massachusetts Institute of Technology \(MIT\) or the University of California at Berkeley were on their way to design and develop "general purpose time\-sharing systems" on different hardware platforms\. Several other companies realized the opportunities in this area and plans were established at other institutions such as Bell Laboratories\. Triggered by the work done at MIT, the IBM Cambridge Scientific Center \(CSC\) undertook the task of developing a time\-sharing system for IBM's System/360 Model 67, which became known as "CP\-67/CMS\." On August 2, 1972 at the "System/370 Advanced Function Announcement," the VM/370 Program Product became available\. By 1972 standards, IBM regarded VM to be "open" because it:

- Provided tailorable source code

Giving the source code in conjunction with the easy\-to\-use service procedure, using "update," opened VM to the creativity and imagination of the system programmers of the VM community\. Problem\-fixes and clever new or additional functions could be developed to meet the needs of the end user and to the benefit of VM\. The "Waterloo Tape," distributed by the University of Waterloo, was the gathering point of these efforts\. Much of the VM/ESA source is still available these days, at no charge\.

- Allowed connections and conversations with other systems

The initial users of VM \(or the predecessors\) were the universities\. They organized into the VM group of SHARE Inc\. Over a VM network used for the research environment \(BITNET and NETNorth\), advice and usability/stability improvements were distributed to other VM users\. When the IBM\-internal network \(VNET\) joined in, one could communicate with an amazing number of IBM systems running any kind of operating system\.

- Was the host for other operating systems

The concept of virtual machines enabled it to support any operating system that was based on the IBM *System/370 Principles of Operations\.* The virtual machine, in order to run an operating system or application, requests services and resources from the Control Program \(CP\)\. CP is designed to manage \(real hardware\) resources, requests for these resources, and the requestors issuing the requests\.

- Allowed snap\-in new function

Many VM end users are capable of writing small "applications" to make their work easier\. Such "applications" are usually written in REXX, commonly called "EXECs," and perform tasks in the area of file management, text writing, electronic mailing, and so on\. Very often they enhance existing applications\.

Many of these EXECs get eventually shared with colleagues, or even land on public tools disks, improving the productivity of whole groups of people\.

VM has a long history of EXEC writing and almost anything can be done using REXX\. Interfaces are available to almost everything\. The need to use assembler or C, which closes the door to many people, does not often arrive\.

Writing application add\-ons is so easy on VM as most applications are either started with REXX EXECs, or have major parts written in REXX\. Another contrast with many workstation applications facilitates this further: VM applications typically use CMS files with readable contents\. This source code exposes program internals, enabling users to add extra bells and whistles\. Writing or changing REXX EXECs is in the scope of many more people than coding programs in, for example, C\.

The arrival of CMS Pipelines in VM further enhances this capability: CMS Pipelines has such a rich set of built\-in functions that writing simple CMS Pipelines applications is very easy and quickly done\.

OfficeVision/VM is a very good example of an application having such openness\. Most installations enhanced their OfficeVision environment by coding some extra REXX EXECs, an example being the generation of formatted mail for holiday requests\. Many of the new functions in OfficeVision where born as local modifications\. Office applications on other platforms are often 100% closed in this aspect: they are limited to functions the designers thought of and implemented\.

The concept and support for many functions implemented in service virtual machines still exists today\. The separation of functions in virtual machines allows debugging of problem virtual machines without affecting other service machines running\. Thus, CP could be kept clean and stable for its task to manage the "clients" and "servers" under its cover\. This implementation however, needed a common interface used by virtual machines in communicating with each other\. The Virtual Machine Communication Facility \(VMCF\) was developed to perform this function\. Later, the Inter\-User Communication Vehicle \(IUCV\) was added\. This more modern communication interface allowed, among other functions, multiple virtual machines to be served simultaneously by a single service virtual machine\. The demand for connecting to other systems also led to the development of products such as Remote Spooling Control System \(RSCS\) and VM/Pass\-Through Facility \(PVM\)\. Using bisync communication, the networking protocol available at that time, line drivers allowed VM systems to connect not only to other VM systems, but also to DOS \(VSE\), OS \(MVS\), or System/6 \(AS/400\) systems and others\. Today VM is exploiting the SNA network technique, using APPC/VM and AVS, as well as TCP/IP and OSI architectures in order to keep the networking capabilities up\-to\-date\. Communication is a critical element of Client/Server computing\. The following list, which is not complete or in any order, points out some examples of VM's contribution to Client/Server\-like implementations:

- APPC/VM using AVS The Advanced Program\-to\-Program Communication\-VTAM\-Support \(AVS\) allows VM to connect to the SNA world\. The Common Programming Interface for Communications \(CPI\-C\) is the standard defined and published by IBM for this environment\. CPI\-C and AVS have been available since VM/SP Release 6 \(1989\)\. Any application using this interface can be connected, regardless of the underlying operating system\.
- APPC/VM using TSAF The Transparent System Access Facility \(TSAF\), based on the Advanced Program\-to\-Program Communication/VM \(APPC/VM\) protocol, allows multiple VM systems to become attached in such a way that shared resources are transparently accessed using bisync or CTC communications\. The group of VM systems is called a collection\. It became available with VM/SP Release 5 \(1987\)\. CPI\-C is also the application interface\.
- SFS The Shared File System \(SFS\) allows read/write sharing on the file level\. Hierarchical file directories, support for alias names, and application program support through Callable Service Library \(CSL\) functions became available with VM/SP Release 6 \(1989\)\. The "Remote SFS" includes SFS data sharing across multiple systems, providing the "Common Directory\."
- CSE Up to four VM systems may build a Cross System Extensions \(CSE\) complex\. The following functions are provided:

Cross system LINK, that allows sharing of minidisk data on shared CKD DASD devices across multiple VM systems Cross system spool on shared DASDs within a CSE complex Cross system MESSAGE, QUERY, and other commands, as well as DIRMAINT, RACF, and APPC/VM support within a CSE complex

- DIRMAINT \(5748\-XE4\)

This program product maintains data over system boundaries from a focal point of control\. It became available in 1981\.

- SQL Guest Sharing

This function allows VSE running in a virtual machine to access and share SQL data on the CMS platform\. DB2/VM \(5688\-103, formerly SQL/DS\) stores data in CMS minidisks and services the access from a service virtual machine\. With the SQL/DS 3\.3 release the Distributed Relational Database Architecture \(DRDA\) is implemented\.

- GDDM\-OS/2 Link or GDDM/PCLK

These products allow GDDM applications running on the host to be accessed from an OS/2 based or DOS based workstation, respectively\. The calculation is done on the host, while the presentation is prepared on the workstation\. For Microsoft Windows environments, the functions of GDDM/PCLK are integrated into PC/3270 Version 3\.0 and later\. There are also applications available for the AIX and the OS/400 environments\.

- CSP \(5668\-813 and 5668\-814\) The Cross System Product \(CSP\) consists of two parts: the application development \(AD\) part and the execution \(AE\) part\. The AD can be run on a workstation, developing applications that are designed to run in other environments\. The application can also be designed in a way that parts of it are executed on a workstation\.
- CMS application multitasking

Today a Client/Server implementation cannot be considered without threading\. In CMS, the equivalent function is called CMS application multitasking\. The function has been provided by VM/ESA, since Release 2\.

- HLLAPI

By providing the 3270\-PC user with an interface to the PC 3270 emulation, the High\-Level Language API \(HLLAPI\) allowed applications that simulated operator actions, such as key strokes\. The function is needed to automate applications on an unattended workstation\.

- REXX\-IUCV \(5785\-LAT\)

This product is designed for IUCV based REXX applications in the CMS environment\. \(REXX\-IUCV has limited availability in specific geographies\.\)

You may have noticed that modern Client/Server products, such as LANRES, ADSM, or LFS/ESA, were missing from the list\. These products, first developed on VM, are discussed extensively in [Part 3, "VM and](<#HDRHPRT400>) [Client/Server" in topic 3\.0](<#HDRHPRT400>)\.
