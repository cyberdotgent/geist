### 3\.2\.2\.3 DCE Cell Directory Service in VM/ESA

VM/ESA Version 2 can participate in a DCE Cell as a DCE Cell Directory Service Client accessing the DCE Directory Server on another system in the DCE Cell\. As mentioned earlier, VM/ESA requires a peer operating system in the DCE Cell that acts as a DCE Cell Directory Server, such as AIX\.

The DCE directory architecture will allow VM DCE client applications access to server data both within the local cell and across multiple cells\. This capability is provided by the Global Directory Agent, which appears as a CDS server \(running on AIX, for example\) to VM's CDS client\. In fact, its actually a bridge to the GDS service \(Section ["Directory](2-4-5.md) [Services" in topic 2\.4\.5](2-4-5.md)\)\. Therefore, providing authorizations exist, VM DCE users can DCE login and applications can issue RPCs across DCE cells\.

The VM/ESA CDS Client components are:

- CDS Clerk and Cache
- CDS Advertiser
- CDS Control Program \(administration utility\)

Usually, application programmers use the Directory Service only to export and import server location information\. This use of the Directory Service is indirect\. The XDS/XOM API will allow an application to access CDS \(not GDS\) data through non\-RPC calls\. Another interface to the Directory is the RPC Name Service Interface \(NSI\) routines which are a group of RPC calls \(*rpc\_ns\_*\)\. These NSI routines allow a programmer to control the association, or binding, of a client to a server during RPC\.
