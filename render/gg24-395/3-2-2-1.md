### 3\.2\.2\.1 DCE Threads in VM/ESA

VM/ESA Version 2 provides support for the OSF DCE threads API\. These DCE threads are implemented as POSIX threads, which in turn are mapped to CMS threads in the CMS multitasking base\. This provides the multithreaded support required by the DCE Kernel, applications, and utilities\.

Both DCE and POSIX threading, as implemented in VM, are based on the POSIX\.1c standard\. However, OSF developed DCE using Draft 4 of the standard and CMS's implementation of POSIX threads is at the Draft 6 level\. There were API revisions made between draft levels that provide a small level of incompatibility\. The DCE Threads implementation in VM solves this by including, with the DCE runtime, library code that adjusts the Draft 4 level DCE expects, to the Draft 6 level CMS POSIX expects\. As an application program can use the DCE API's, the POSIX API's, or native CMS API's, the programmer needs to decide which thread API he will be using; for example, he can use pthread\_create \(DCE\) or ThreadCreate \(CMS\)\. Some influences on this decision are:

- Application portability

POSIX threads are at Draft 6, DCE threads are at the Draft 4 level\. Be aware of this if the application is intended to operate on another platform\. Also, the DCE and POSIX threading semantics differ from CMS's native multithreading semantics\. You need to research these differences\.

- Other API's required throughout the application

If the application will mostly use POSIX API calls, then it would be best to use POSIX thread API\.

An application programmer can use threads to benefit from the concurrency\. However, having multiple threads of control, in many cases, introduces a higher level of complexity than a single thread of control\.

It is worth noting that DCE/POSIX/CMS multithreading will automatically take advantage of multiple virtual processors, if they are defined for a virtual machine\.
