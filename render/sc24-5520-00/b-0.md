# B.0 Appendix B.  Monitor Records

<a id="HDRMONAPP"></a>

**General** **Description** **of** **the** **Monitor** **Records** The format, content, and descriptions of the monitor records produced by CP are product-sensitive programming information. See Special Notices in topic [NOTICES](notices.md) for a warning on the use of this information. The monitor records generated by the VM/ESA monitor facility are placed in the DCSS defined for Monitor. The starting and ending addresses of the data are communicated to application programs by the *MONITOR CP system service. PSPI The records are arranged by domain number and, within each domain, by record number. The domains associated with each number are: **Domain** **Number** **Domain** **0** System **1** Monitor **2** Scheduler **3** Storage **4** User **5** Processor **6** I/O **7** Seek **10** Application data The placement of the records within the DCSS is not guaranteed to be in any particular order by domain or within domains. This is especially true for event processing. Unless otherwise stated, all counters are cumulative counters. That is, the application program processing the data must subtract an interval's data from the previous interval value to determine how much a particular counter changed from one interval to the next. Cardinal counters are counters whose values are incremented or decremented, such as the number of logged-on users. Cardinal counters, therefore, represent a state of the system at the time it is sampled. **Where** **to** **Find** **the** **MONITOR** **LIST1403** **File** The file containing the monitor records was loaded onto your base CP object disk (194) at the time VM/ESA was installed on your system. The name of the file is MONITOR LIST1403, plus whatever mode designation is given to the CP object disk (194). **To** **Print** **the** **File** To print this file, issue whatever EXEC you use to print files that are already formatted for printing. Records that have changed are flagged by revision bars (|) in the left column. [Table 66](#TBLMRCHGS) lists monitor records that have changed. In the table, the following reasons for change are used: New *dat*a*--da*ta is either appended to the bottom of a record or placed in unused fields that were reserved for IBM use. Dele*ted--de*leted data becomes reserved fields. Deleted data does not affect the layout of the rest of a record. New *rec*o*rd. T*his is a new record. Comm*ents cha*n*ged--se*e the comments in the record layouts provided on the product tape. Their contents and locations are not changed. While comments in many records have been reworded or changed, mostly for clarification, only those that may need your attention are listed in this table. Rena*med--so*me fields are renamed to reflect internal CP changes. Their contents and locations, however, are not changed. In some cases, a field is not only renamed but also redefined to list its components. The field's contents should be referenced by the individual component instead of by its encompassing structure. For example, bit 7 of a byte should be referenced by the X'01' test mask instead of by the whole-byte value of X'01', because there is no guarantee or requirement that the first 7 bits of the byte are all zero.
